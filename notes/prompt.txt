
Aquí tenés el plan maestro para integrar **Multi-sucursal en la V1**:

## Plan: Integración Multi-Sucursal en V1

### Fase 1: Actualización de Documentación (docs)
*El objetivo es reflejar la nueva arquitectura antes de tocar una línea de código.*
1. **pdr.md**: Actualizar §2.7 (Roles) para incluir `SUPER_ADMIN` y definir que la sucursal es el alcance natural de los reportes.
2. **technical_guide.md**:
    - Agregar el modelo `Branch` en §3.1.
    - Definir la relación de `User`, `Shift`, `CashRegister`, e `InventoryItem` con `Branch`.
    - Documentar el endpoint de resumen `/reports/branches-summary` (solo para `SUPER_ADMIN`).
3. **requirements.md**: Añadir FR sobre gestión de sucursales (creación/edición por super admin) y el nuevo nivel de acceso.
4. **`indice_pdr.md`**: Ajustar el mapa de relaciones para incluir la entidad `Branch`.

### Fase 2: Actualización de Schema (schema.prisma)
*El objetivo es establecer la nueva arquitectura de datos.*
1. **Nuevo Modelo `Branch`**: Definir campos `id`, `name`, `address`, `active`.
2. **Actualización de `User`**: Agregar `branchId String?` y relación a `Branch`. Actualizar `UserRole` para incluir `SUPER_ADMIN`.
3. **Actualización de Entidades Locales**:
    - `Shift`, `CashRegister`, `InventoryItem`: Agregar `branchId String` y relación a `Branch` (required, pues toda operación debe pertenecer a una sucursal).
    - `InventoryItem`: Cambiar `@@unique([sku])` por `@@unique([branchId, sku])` para permitir SKUs repetidos en distintas sucursales.
    - `CashRegister`: Cambiar `@@unique([name])` por `@@unique([branchId, name])`.
4. **`Customer`**: Agregar `passwordHash String?` para habilitar el login de clientes en futuras fases.

### Fase 3: Actualización del resto del código (Backend)
*El objetivo es implementar la lógica centralizada de filtrado.*
1. **Infraestructura**:
    - Crear el módulo `BranchesModule` (CRUD sucursales).
    - Implementar el helper `getEffectiveBranchId()` en `src/common/helpers/` para centralizar la lógica de filtrado de sucursal.
    - Actualizar `AuthGuard` y `RolesGuard` para considerar el nuevo rol `SUPER_ADMIN` y el contexto de sucursal.
2. **Lógica de negocio**:
    - Inyectar el filtro de `branchId` en todos los servicios de entidades locales (`InventoryService`, `ShiftService`, etc.) usando el helper.
    - Ajustar los reportes existentes: todas las consultas deben usar `branchId` del usuario (o `branchId` del query param si es `SUPER_ADMIN`).
    - Implementar `GET /api/v1/reports/branches-summary` exclusivo para `SUPER_ADMIN`.
3. **Seeders**:
    - Actualizar seeders para crear al menos una sucursal y asignar los datos iniciales (usuarios, inventario, turnos) a dicha sucursal.
