SECCION 3. PEDIDOS Y ESTADOS
================================================================================

[AMBIGUA] 3.1 Maquina de estados definitiva de un pedido
--------------------------------------------------------------------------------
Pregunta original:
  Cual es la maquina de estados definitiva de un pedido
  (ej. registrado -> preparando -> listo -> entregado -> cerrado)?

Respuesta actual en el doc:
  "El nuevo sistema debe tener una maquina de estados segun sea lo mas
   adecuado sin llegar a ser complejo."

Por que es ambigua:
  No define los estados concretos, ni las transiciones permitidas, ni que
  evento dispara cada cambio (ej. quien marca "listo": cajera o despachadora?).
  Sin esto no se puede modelar la entidad Order.

Que falta definir:
  - Lista exacta de estados (ej. PENDING_PAYMENT, PAID, PREPARING, READY,
    DELIVERED, CANCELLED).
  - Transiciones validas entre estados.
  - Rol responsable de cada transicion.
  - Estados terminales (cuales cierran el pedido).

[AMBIGUA] 4.1 Como se registran los vales en el sistema
--------------------------------------------------------------------------------
Respuesta actual en el doc:
  "...se puede anadir al flujo de venta una opcion de pago como vale
   o simplemente tener una interfaz dedicada (elegir la opcion que sea
   mas simple y efectiva)."

Por que es ambigua:
  Se delega la decision al desarrollador. Esto impacta directamente el modelo
  de datos (Payment vs Voucher como entidades separadas) y el flujo de UI.

Que falta definir:
  a) Vale como metodo de pago dentro del flujo normal de venta.
  b) Vale en interfaz dedicada separada del flujo de venta.
  c) Ambos.


[AMBIGUA] 4.6 Politica de descuento interno al personal
--------------------------------------------------------------------------------
Respuesta actual en el doc:
  Describe la PRACTICA ACTUAL (vender Porcion Media a 23 Bs registrandola
  como Cuarto de Pollo) pero NO define una politica deseada para el nuevo
  sistema.

Por que es ambigua:
  El nuevo sistema debe replicar este "hack" o se debe formalizar como
  un descuento real / tipo de venta especial?

Que falta definir:
  - El nuevo sistema debe permitir un "descuento de personal" formal?
  - Si si: que rol lo autoriza, en que horarios aplica, como se refleja
    en arqueo e inventario?
  - Si no: se mantiene la practica actual de mapear a otro plato?
